## How the inventory is made

- The API list is the `rpc.API` literals of `quaiapi.GetAPIs`
  (internal/quaiapi/backend.go:197) and `Quai.APIs` (quai/backend.go:294),
  parsed from the source in registration order, with the zone-only block.
  The registry of go-quai's `rpc.Server` (rpc/service.go) lists every method
  and subscription; each row names the Go function that serves it.
- "HTTP" and "WS" say whether a zone node started with no flags serves the
  name. The oracle builds `makeConfigNode`'s configuration (cmd/utils/cmd.go
  `defaultNodeConfig`, then `SetNodeConfig` over the start command's flags),
  starts the production `node.Node` with it on loopback, and probes every
  name: `rpc.Server` answers -32602 for a registered name before it runs the
  handler and -32601 for an unknown one. No handler runs.
- Classes: (a) read-only chain or state, with the pool submissions;
  (b) mining, block templates or Stratum; (c) admin or debug; (d) personal
  or signer.

## Default endpoints of a go-quai zone node

- HTTP on localhost:9200 (zone [0 0]): modules `net, web3, quai, net` (node/defaults.go plus `defaultNodeConfig`).
  No API has the namespace "web3", so the endpoint serves
  `net`, `quai`, `rpc`.
  `--rpc.http-api` replaces the list.
- WebSocket on 127.0.0.1:8200: `setWS` always sets the
  modules from `--rpc.ws-api`, whose default is empty, and `RegisterApis`
  (node/rpcstack.go:490) then registers every public API:
  `debug`, `eth`, `net`, `quai`, `rpc`, `txpool`, `workshare`.
  So `eth_*`, `txpool_*`, `workshare_*` and the public `debug_*` methods are
  served by default, but only over WebSocket.
- Subscriptions (`*_subscribe`) work over WebSocket only; over HTTP
  `rpc.Server` answers "notifications not supported".
- A `*_unsubscribe` call reaches one handler for every namespace, even an
  unknown one (rpc/handler.go `handleCall`).
- The Rust node serves all its methods over HTTP and over WebSocket on one
  listen address. It therefore also serves `txpool_*` and `eth_*` over
  HTTP, as go-quai does with `--rpc.http-api` naming them.

## Where the Rust node answers differently

Each served name answers with go-quai's JSON and error texts over the Go
oracles (`fixtures/protocol/rpc-parity.json`, `rpc-calls.json`,
`filters.json`, `qi-rpc.json`, `txpool.json`, `fixtures/native-rpc`).
What still differs:

- Transports: the Rust node serves every name above over HTTP and
  WebSocket on one address; a default go-quai node serves `eth_*` and
  `txpool_*` over WebSocket only.
- `quai_clientVersion` and `eth_clientVersion` name the Rust node
  (`quai-rust/v<version>`); `rpc_modules` lists the namespaces the Rust
  node serves (the same on both transports).
- The address UTXO index (`--node.index-address-utxos`, off by default):
  `quai_getOutpointsByAddress` and the
  Qi balances answer from the UTXO set, as an indexing go-quai node does;
  `quai_getLockedBalance` of a Quai address, `quai_getSupplyAnalyticsForBlock`
  and `quai_rewardAnalytics` answer as a default node does.
- Live events: the `quai-node rpc` view is frozen and sends no event, as a
  go-quai node that is not syncing. `quai-node run` publishes its heads
  ("newHeads", "newHeadsV2", "logs", block filters and "accesses" by
  transaction) but not yet its appended blocks ("newChainBlocks",
  "newChainBlocksV2"), its unlocks ("accesses" by unlock), its rolling fee
  window (`txpool_getRollingFeeInfo` answers go-quai's "no transactions
  processed" error) or its peer counts (`net_peerCount` answers 0x0, as
  go-quai without a p2p backend).
- "accesses" matches the sender of a Quai transaction; go-quai matches it
  only when the transaction's sender is cached (`Transaction.From`), as it
  is in a block the node processed.
- go-quai drops events that a busy subscriber cannot take (non-blocking
  sends into channels of 0 or 10 entries); the Rust node queues up to
  4,096 messages per connection.

## Mining phase (class b)

Not ported here: the mining phase comes last. A default go-quai zone node
builds a pending header on every new head and every second whether or not
a miner is attached, so most class (b) methods answer on a non-mining node
(the notes above say what). No wallet needs them: Quais.js and Pelagus
use none (Quais.js exposes `getPendingHeader()` without calling it).

What the Rust node needs to serve them:

1. A pending-header builder (core/worker.go, core/slice.go): the prime,
   region and zone header parts and their combination; transaction
   selection from the Quai and Qi pools with the Qi fee conversion, inbound
   ETXs, the ETX set and the gas and state budgets; uncle and workshare
   selection from three 1,000-entry caches; coinbase ETXs for shares at
   depth 3 to 4; `FinalizeAssemble` (EVM, UTXO and ETX-set roots, receipts,
   manifest); the coinbase choice and lock byte; the KawPow AuxPow
   placeholder.
2. The pending-header cache and its triggers: the best pending header in
   memory and on disk, rebuilt on each head, every second and when local
   transactions wait, with the "pendingHeader" feed.
3. The body and AuxPow caches keyed by seal hash (and seal hash with the
   signature time), kept across restarts.
4. Aux templates: gossip intake with the 2-of-3 MuSig2 check, the newest
   template per algorithm with the hardcoded defaults, the donor coinbase
   and header builders (Ravencoin 120 bytes, BCH and Litecoin 80 bytes),
   the coinb1/coinb2 split, merkle roots and the getblocktemplate JSON.
5. Workshare intake: gossip validation with the runtime P2P threshold,
   `AddWorkShare` and its feed ("newWorkshares").
6. Submissions: the protobuf work-object codecs, workshare classification,
   donor block parsing (`SubmitBlock`), `CalcOrder`, local block
   construction and gossip publication.
7. Proof of work: ProgPoW and KAWPOW with the DAG, SHA256d and scrypt donor
   hashes, and the entropy thresholds.
8. MuSig2 verification (signing only on a signer node), and the optional
   `--node.index-address-utxos` indexes (donor hash, workshare hash).

A default go-quai node without a miner also does not relay wallet
transactions: gossip has no transaction topic, so a local transaction
leaves the node only inside a share mined on its template, or through
`--txpool.sharing-clients` (core/tx_pool.go, core/slice.go).
